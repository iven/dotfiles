本文介绍在 Raft 中为项目开发一个新特性的协作方式。

## 角色

在 Raft 频道中有几种角色：

* 用户：需求的提出者，指挥所有人协作
* 开发者：开发负责人，与用户直接沟通需求
* 主持人：负责维护秩序，让所有人按照流程办事。禁止参与任何其他事情（需求讨论、用户疑问、验收等）
* Review 专家：负责对方案和代码进行评审。禁止参与任何其他事情（需求讨论、用户疑问、验收等）
* 呈现者（可选）：部分项目可能依赖于呈现者将程序运行起来，呈现给用户。禁止参与任何其他事情（需求讨论、用户疑问、验收等）

在开始前，首先识别你自身是 Agent Team 中的哪一种角色，然后阅读自身角色指导文档（roles/*.md），按照文档进行工作。

## 全员流程

* **需求提出**：用户提出需求
* **需求对齐**：开发者跟用户确认需求，如果需求太过模糊，可以使用 grilling skill 进行询问。回复必须发送在 thread 中。用户与开发者讨论，直到用户明确通过需求，进入下一步。
  - 常见错误1：将用户的需求当作开发许可，直接开始开发
  - 常见错误2：将回复发送在频道中
  - 常见错误3：开发者以外的角色自作聪明地帮助分析问题
  - 常见错误4：用户未明确表明需求通过，就自作聪明地认为可以进入下一步
* **提出草案**：需求确定后，开发者给出技术草案，发送在 thread 中，同时 @ 主持人开始主持流程，进入下一步。
* **方案评审**：主持人为每个专家创建评审任务，并进入「方案评审」流程，产出物是最终技术方案，开发者询问用户是否可以开始开发，用户明确同意后，进入下一步。
  - 常见错误：用户未明确表明可以开始开发，就自作聪明地认为可以进入下一步
* **技术开发**：开发者在项目的 `.worktrees` 目录下创建 worktree 并开始编码，确保 Lint、Test 等所有 check 都通过，然后在 thread 中发送通知，进入下一步
* **代码评审**：主持人为每个专家创建评审任务，并进入「代码评审」流程，产出物是最终技术方案，开发者询问用户是否可以提交代码，用户明确同意后，进入下一步。
* **代码提交**：开发者提交代码，合并到主仓库的 main 分支，并删除 worktree 和临时分支。无需推送到远程。

注意：
* 所有角色必须严格按照流程办事，严禁跳过流程
* 主持人全程监听会话，认准下一步的准入规则，阻止流程偏离。
* 每次在 thread 中发送消息，末尾都必须加上步骤标记，比如：`[Agent Team - 需求对齐]`
* 所有会话必须发送在 thread 或者任务中，禁止发送到频道中，或者发送 DM。
* 如果用户没有回答某些问题，意味着用户没有看到该信息，决不能认为用户对方案进行了默认。
* 向用户追问前文问题时，必须附上原文可点击链接，方便用户点击查看。
